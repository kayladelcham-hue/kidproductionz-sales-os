# Beginner campaign flow

The primary setup now has three stops: save what you sell to the existing user profile, choose business type/city/state together, and find customers. The search summary has Edit search; detailed configuration remains in secondary tools. Saved records, notes, decisions, outreach history and campaign IDs are unchanged.

Automatic organization uses POST /api/campaigns/resolve-target with structured customer industry/city/state, not the seller's industry or a display-name match. The backend checks only campaigns owned by the current user, normalizes casing/spacing/punctuation and known singular/plural category variants, and reuses the selected owned campaign when its structured target matches, otherwise the first matching non-archived campaign. It does not merge duplicate historical campaigns. Unknown legacy targeting is not inferred from a name.

A new market gets a deterministic owner-and-target hash as its campaign slug, with the existing database unique slug constraint as the concurrent creation guard. Losing transactions roll back and read the winning campaign. No schema migration, new table or environment variable is required. Display names such as Atlanta Restaurants and Orlando Hair Salons are presentation only. Renaming through the existing Campaigns tools preserves identity. Changing search criteria resolves another market without renaming campaigns or relocating records. An auto-created campaign later archived or retargeted can return a conflict requiring an explicit manual campaign selection/creation; records are never silently moved.

The shared campaign picker is available in the menu and existing topbar placements. Its ＋ New campaign sentinel opens a name/type/area dialog without selecting the sentinel. Recent search criteria prefill the fields. The existing creation API uses one stable UUID across retries. A retry checks whether that exact owned campaign already exists before POSTing again, covering a lost response or failed list refresh. Cancellation and errors preserve the current selection; successful creation refreshes and selects the new campaign. Custom names and existing rename tools remain available.

Search preparation resolves the market before starting a search. Resolver failure leaves inputs editable and starts no search. A pending search request keeps its UUID through connection failure and setup restoration, using the discovery endpoint's existing idempotency. Campaign selection refreshes at the end of the search attempt, avoiding a component remount in the middle of persistence. Selected campaign is stored locally and validated against the server's owned campaign list on reload.

Home's contact card now appears after the business-card results, and New search is a compact control. Contact is a fourth bottom-navigation destination leading to existing outreach tools.
